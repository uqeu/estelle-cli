Where a note is red it is a defect or a conflict I want a ruling on. Where it is pink it is a question. Where it is green it is something already right that I would not change.

    It is ctrl+g now, everywhere, and the hint says the same thing. You put it exactly right: Windows has no option key, macOS has no alt key, and both have control — so control is the only modifier that can mean one thing on both machines. This was alt+m, which macOS eats as a compose key and turns into µ in the composer; the binding sat four lines above a comment forbidding it, which is why nobody caught it by reading the code. A check now scans this file and goes red on any alt+<letter> chord.
    Why not ctrl+m, which is the letter you would expect — and the change it forced to your hint row. Ctrl+M is carriage return, the same bytes as enter. This binary does not turn on the newer keyboard protocol that can tell them apart, so a ctrl+m binding would swallow every enter and sending a message would stop working.

It read enter send · tab repo · ctrl+s spend · ctrl+m models · esc stop on every frame — your line, verbatim, picked three times — and one of those five keys could never exist. The rule that settled it: the hint and the binding must agree, and when they cannot both be right, the working binding wins. The fourth pair is ctrl+g context now: a real binding that had no hint at all, on a pane nobody can reach by a key they were never told about.
